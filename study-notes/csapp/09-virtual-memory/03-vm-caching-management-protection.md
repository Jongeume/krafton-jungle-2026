## 캐싱 도구로서의 VM

가상메모리 - **디스크에 저장된** N개의 바이트 크기의 셀 배열  
(가상메모리라 무형일줄 알았는데, 실존했다.)  
각 바이트는 특정한 가상주소를 가짐.  == 가상주소는 배열의 **인덱스**로 작용

VM system - 가상메모리를 블록 단위로 분할하여 관리. (배열을 블록 단위로, 가상주소들을 블록단위로.)  
가상페이지 = 분할된 블록들 (= 분할된 가상주소들)  
가상페이지의 크기: P = 2^p 바이트  
물리페이지의 크기: P 바이트

물리페이지는 **페이지 프레임**(page frame)이라고도 부른다.

- unallocated : 비할당된 페이지. 관련 데이터X, 디스크상에 공간X,  
- cached : 현재 물리 메모리에 캐시되어 할당된 페이지  
- uncached : 물리 메모리에 캐시되지 않은 할당된 페이지

## 9.3.1 DRAM 캐시

VM 시스템 캐시 - 메인메모리로 가상페이지 캐싱.

읽기속도 : SRAM > DRAM(메인메모리) >>> 디스크(가상페이지)

~~캐시 미스 비용 = 잘못된 캐시 접근 -> 다시 접근 (이때 첫번째 바이트 접근 비용 발생?)~~  
→ **정정** : 캐시 미스 비용 = 미스가 났을 때 그 페이지를 **디스크에서 가져오는** 비용. DRAM 캐시 미스는 디스크에서 채우기 때문에 비싸다. (디스크는 첫 바이트를 읽는 것이 연속 바이트보다 약 10만 배 느리다)

연속 바이트 접근 비용 < 첫번째 바이트 접근 비용

캐시 미스 비용, 첫번째 바이트 접근 비용 증가 => 가상페이지 **크기**가 커짐 (보통 4KB ~ 2MB)  
(왜? 어차피 첫 접근이 비싸니 더 큰 블록으로 한번에 많은 양을 읽자.)

DRAM 캐시는 완전 결합성 = 모든 VP는 PP에 둘 수 있다.

디스크의 큰 접근 시간 때문에 DRAM은 항상 write-through 대신에 write-back 사용

## 9.3.2 페이지 테이블

VM 시스템은 가상페이지(디스크에 저장된 분할된 가상주소들)가 DRAM 어딘가에 캐시 되었는지 결정하기 위한 방법을 갖고있어야한다.

어떤 물리페이지(= DRAM 블록)를 캐싱했는지 결정해야 한다.

미스났을때 :  
1. 디스크에 가상페이지가 어디 저장되어 있는지 결정  
2. 물리메모리 (메인메모리)에서 희생자페이지(물리페이지 = DRAM 블록) 선택  
3. 가상페이지를 디스크에서 DRAM으로 복사해서 희생자 페이지 교체

- PT(페이지 테이블)  
  - 가상페이지를 물리페이지로 매핑  
  - 물리메모리에 저장된 **자료구조**. (정정 : '조합'은 OS 소프트웨어 + MMU의 주소 번역 하드웨어 + 페이지 테이블, 이 셋이 합쳐져 기능을 제공한다는 뜻이다)  
  - PTE(페이지 테이블 엔트리)의 배열

- 주소 번역 하드웨어 (MMU 내에 있음) : 가상주소를 물리주소로 변환할 때 마다 페이지 테이블을 읽음.

- PTE(페이지 테이블 엔트리)  
  - 유효비트(valid) : VP가 현재 DRAM에 캐시되어 있는지 나타냄  
  - 주소 필드의 구성  
  1. 유효비트 세팅 O : VP가 캐시되어 대응되는 DRAM의 PP의 시작을 나타냄.  (=cached)  
  2. 유효비트 세팅 X :  
    2.1) (PP == NULL) NULL 주소는 VP가 아직 할당되지 않았음을 나타냄, (=unallocated)  
    2.2) (pp != NULL) 그렇지 않은 경우, 주소는 디스크상의 VP의 시작부분을 가리킴. (=uncached)

DRAM 캐시는 완전결합성 = 어떤 가상페이지든 **어느 물리페이지 칸에나** 넣을 수 있다. (~~물리페이지가 모든 가상페이지를 포함~~ · ~~어디든 접근 가능~~ 이 아니라, **배치**가 자유롭다는 뜻)

연습문제 9.2) PTE 개수 = 2^(n-p)  (검증 : 아래 네 답 모두 맞음)  
1. (12-10 = 2 ) -> 2^2  
2. (16-14 = 2) -> 2^2  
3. (24-21 = 3) -> 2^3  
4. (36 - 30 = 6) -> 2^6

## 9.3.3 페이지 적중

CPU가 DRAM에 캐싱된 가상메모리의 VP 워드 한 개를 읽을때.

주소번역하드웨어(MMU에 내장)은 VP를 통해 PTE에 접근 -> 메모리에서 읽음  
유효비트 세팅O = VP가 메모리에 캐시되어 있다. -> 주소번역하드웨어는 VP가 메모리에 캐시된걸 안다.  
PTE 내에 물리메모리주소(= PP내의 캐시된 주소의 시작을 가리킴)를 사용해 해당 워드의 PA 구성.

## 9.3.4 페이지 오류

- 페이지 오류: DRAM 캐시미스

주소번역하드웨어가 메모리에서 PTE 읽고 유효비트 X (VP 캐시X) -> 페이지 오류 예외  
- 페이지 오류 예외 (예시)  
커널 내에 페이지 오류 예외 핸들러 호출 -> 희생자페이지( PP3 -> VP4 선택)  
-> VP4가 변경되었다면 ?-> 커널이 다시 디스크에 복사.

어떤 경우든 커널은 VP 4에 대한 PTE 수정(VP 4가 메인메모리 캐시되지 않음 반영) -> 커널은 VP 3를 디스크에서 메모리 내의 PP 3으로 복사 -> PTE 3 갱신 후 리턴. -> 오류  인스트럭션 재시작.

오류 인스트럭션 재시작-> 오류 VA를 주소 번역 하드웨어로 재전송. -> VP 3 캐시되어있음. -> 페이지 적중 정상.

- 페이징 (=스와핑) : 디스크와 메모리 사이에 페이지를 전송하는 동작

디스크 -> DRAM : 페이징되어 들어옴  
DRAM -> 디스크 : 페이징되어 나감

용어가 다르게쓰임  
SRAM 캐시의 **블록**(block)을 VM에서는 **페이지**(page)라고 부른다

미스발생시) 요구페이징 : 미스가 나는 **마지막 순간까지** 페이지를 들여오지 않고 기다리는 전략  
현대의 모든 시스템은 요구 페이징 방식 사용.

## 9.3.5 페이지의 할당

malloc 호출 -> VP는 디스크 상에 공간 만듬 -> PTE로 디스크에 새롭게 만든 VP 가리킴.

## 9.3.6 지역성

동작 집합(working set) = 거주 집합(resident set) = 프로그램이 실제로 활발히 쓰는 **작은** 페이지 집합  
--> 이 집합이 한 번 메모리에 들어오면, 그 뒤의 참조는 히트다.

페이지 집합 크기가 물리 메모리보다 크면, 쓰레싱 상황 연출 가능  
쓰레싱 = 페이지들이 연속적으로 페이징해서 들어오고 나가고 반복.

## 9.4 메모리 관리위한 VM

운영체제는 각 프로세스에서 별도의 페이지 테이블을 제공, 별도의 **가상 주소 공간**(프로세스마다 하나씩)을 제공함.

ex)  
프로세스 i 에 대한 PT : VP 1 -> PP 2, VP 2 -> PP 7  
프로세스 j 에 대한 PT : VP 1 -> PP 7, VP 2 -> PP 10  
= 다수의 VP들이 동일한 공유된 PP에 매핑될 수 있다.

- 링킹 단순화  
  - 코드와 데이터가 물리 메모리 내에 실제 위치와 상관없이 동일한 포맷을 사용.  
  - 코드와 데이터의 위치에 독립적인 완전히 링크된 실행가능 파일 생성 가능

- 로딩 단순화 (안 읽혔던 부분 — 정리)  
  - 로더는 코드와 데이터를 메모리에 **복사하지 않는다**. 가상 페이지를 할당하고, PTE를 valid 0 으로 둔 채 실행 파일 안의 해당 위치를 가리키게만 한다  
  - 실제 복사는 그 페이지를 처음 참조할 때 페이지 오류로 자동으로 일어난다 (요구 페이징)

- 공유 단순화  
  - 프로세스들이 코드와 데이터를 공유하기 바람직할 때,  
  - 서로 다른 프로세스에 들어 있는 VP들을 동일한 PP로 매핑가능 (위에 예시)

- 메모리할당 단순화  
  - 연속적인 가상메모리 페이지를 할당함  
  - 물리 메모리 내의 위치한 k개의 임의의 물리페이지(랜덤하게 흩어져 있음)로 매핑  
  - 페이지 테이블 덕분에 운영체제는 물리 메모리에서 k개의 연속적인 페이지 안찾아도됨. -> 9.18 그림 -> 9.7 1,2,3단 페이지, 4단페이지 Field

## 9.5 메모리 보호를 위한 도구로서의 VM

사용자 프로세스는 자신의 읽기 **전용**(read-only) 코드 섹션을 수정하도록 허용되지 않아야함.  
또한 커널 내의 코드와 데이터 구조들도 읽거나 수정할 수 없어야함.

모든 관련 프로세스들이 명시적으로 허용하지 않았다면, 다른 프로세스의 사적 메모리를 읽거나 쓸 수 없어야 함.

주소 번역에서 접근제어방식)  
1. CPU가 주소를 만들때마다 PTE를 읽기 때문에 PTE에 허가 비트를 추가 ->  
2. 주소번역하드웨어 -> 가상페이지 내용 접근 제어함.

어떤  인스트럭션이 허가사항 위반시  
1. CPU는 일반 보호 오류를 발생시킴  
2. 커널 내의 예외 핸들러로 제어를 이동 시킴.  
3. 그 핸들러가 SIGSEGV 를 위반한 프로세스로 보냄  (정정 : 2와 3의 순서가 바뀌어 있었다)  
4. 이 예외를 리눅스 쉘은 "세그먼트 오류"라고 보고함.

## 궁금한점

- CPU에서 가상주소를 생성하는데 왜 가상메모리는 디스크에 저장된 N개의 바이트 크기의 셀 배열로 구성되고, 각 바이트는 특정한 가상주소를 가지는가.  (가설: 메인메모리에서 N바이트 워드를 CPU에 선입할 때, 워드는 디스크에 가상페이지였고, 그 가상페이지가 메인메모리에 캐싱되어 있어서? )

  - **결론**: **가상주소 = 배열의 인덱스, 그 인덱스 칸의 바이트 = 실체값(데이터).** 원본 배열은 디스크에 있고, CPU가 실제로 읽는 건 DRAM에 캐싱된 페이지 복사본이다. 디스크에 VA를 "저장"하는 게 아니다. (`char a[100]`에서 a[5]의 5가 메모리에 저장되지 않는 것과 같다. 위치가 곧 인덱스.)

  - **왜 "배열 + 바이트마다 주소"인가**: CPU의 load/store가 바이트 단위 주소를 받고, 물리 메모리도 "M바이트 배열, 물리주소 = 인덱스"로 보인다. 프로그램에게 같은 모양(평평한 바이트 배열)을 더 크게 보여주는 게 가장 단순한 약속.

  - **왜 "디스크에"인가**: 주소공간(x86-64 실제 2^48 = 256TB)이 DRAM보다 훨씬 크다. 전체 배열의 원본을 담을 수 있는 건 아래층의 큰 저장장치(디스크)뿐 → DRAM은 원본 일부의 **캐시**. (L1이 DRAM을 캐싱하는 관계가 한 칸 아래로 내려간 것)

  - **접근 흐름**: CPU가 VA 계산 → MMU가 페이지 테이블에서 PTE 확인 → valid=1이면 PA로 변환해 DRAM에서 읽음(hit) / valid=0이면 page fault → OS가 디스크에서 DRAM으로 페이지 복사 → 명령 재실행.

  - **CPU는 VA를 어디서 얻나**: VA는 갑자기 나오는 게 아니라 명령어가 계산한 평범한 숫자.  
    - 명령어 fetch: PC(`rip`) 값 / load·store: 유효주소 = 레지스터 값 + 변위 (`mov rax, [rbx+8]` → rbx + 8)  
    - 숫자의 최초 출처: 링커(코드에 박힌 주소·변위), 커널 execve(rip = 진입점, rsp = 스택 VA 초기값), mmap/malloc(커널이 골라준 VA가 포인터 변수에 저장)  
    - CPU는 그 숫자가 "가상"인지 모른다. MMU가 VA로 해석해 변환할 뿐. → "디스크 배열 + 인덱스 = VA"는 CPU가 아니라 **OS와 MMU가 숫자 위에 씌운 정의**.

  - **VA 숫자가 실제로 존재하는 곳**: 레지스터·포인터 변수 — 일반 데이터 값으로. 디스크에는 페이지 **내용**만 있고 VA는 없다. (정정 : 페이지 테이블에도 VA는 저장되지 않는다. VPN은 표의 **인덱스**이고, 표에 적히는 건 PPN 또는 디스크 위치다)

- 가상 주소 공간 vs 가상 메모리  
  - 가상 주소 공간은 가상주소들의 집합. (번지수 목록 자체)  
  - 가상 메모리는 바이트 배열. 가상주소를 인덱스로 사용. (번지수 = 가상주소와 그 칸의 내용 = 바이트값 )
