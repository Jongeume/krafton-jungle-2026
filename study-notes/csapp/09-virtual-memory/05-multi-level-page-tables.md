# 9.6.3 다중 레벨 페이지 테이블

> 진척도 이슈 : [#204](https://github.com/Jongeume/krafton-jungle-2026/issues/204)

## 그림 9.17 — 두 단계 페이지 테이블 계층

![study-09-fig-9-17-two-level](assets/study-09-fig-9-17-two-level.svg)

- 왜 필요한가 : 페이지 테이블을 한 덩어리로 두면 너무 크다 (32비트·4KB·PTE 4B → 프로세스마다 4MB, 48비트·PTE 8B → 512GB). 그런데 프로그램은 주소공간의 극히 일부만 쓴다

- 아이디어 : 표를 **여러 단계로 쪼개서**, 안 쓰는 구간의 표는 아예 만들지 않는다

- 구조 (32비트 · 4KB 페이지 · PTE 4B)  
  - 레벨 1 PTE 1024개. PTE 하나 = **4MB 청크**(1024 페이지 × 4KB)를 담당  
  - 청크 안에 할당된 페이지가 **하나라도 있으면** 그 PTE가 레벨 2 테이블을 가리킴 (그림에서 청크 0, 1, 8)  
  - 청크 전체가 미할당이면 레벨 1 PTE = null → **레벨 2 테이블이 아예 없다** (그림에서 청크 2 ~ 7, 9 ~ 1023)  
  - 레벨 2 테이블 하나 = PTE 1024개 × 4B = 4KB = 페이지 하나 크기

- 메모리 절약 두 가지  
  - 1\. 레벨 1 PTE가 null이면 레벨 2 테이블을 만들지 않는다 (대부분의 주소공간이 미할당)  
  - 2 레벨 1만 항상 메모리에 두고, 레벨 2는 필요할 때 만들고 page in / out. 자주 쓰는 레벨 2만 메모리에 캐시됨

- 주소 : VA = (VPN1 | VPN2 | VPO) = (10비트 | 10비트 | 12비트)

- 번역 : 레벨 1[VPN1] → 레벨 2 테이블의 주소 → 레벨 2[VPN2] → PPN → PA = (PPN | VPO)  
  - k단계 테이블이면 **PTE를 k번 읽는다** → 번역 비용이 늘어남 → **TLB**가 이 비용을 줄여 줌

- 64비트(x86-64) : 4단계 × 9비트(PTE 8B, 표 한 조각 = 4KB = 512개) = 36비트 VPN + 12비트 VPO = 48비트
